---
title: Migrate from MySQL to PostgreSQL
---

This is a legacy migration path. The released schemas verified for this page are the matching MySQL and PostgreSQL
Core `10.1.4` images, which use storage interface `7.1`. Current Core releases use a newer storage interface. Do not
assume that schemas from different Core versions are compatible, and never use an unpinned image tag for this work.

## Before you start

Treat this as a manual, high-risk database migration. SuperTokens does not provide a supported automated
MySQL-to-PostgreSQL migration procedure on this page. Do not use generic dump and import scripts: a naive CSV-based
migration can silently drop rows, shift columns, corrupt escaped or binary values, violate constraints, or report
success after a partial import. Plan and validate the procedure with your SuperTokens support contact or a maintainer
who understands the released Core storage schemas. Do not test it directly on production data.

Do not begin the production migration until a maintainer or your support contact has reviewed a migration-specific
procedure and all of the following are true:

- Record the exact source Core image tag, storage schema version, database name, schema, and custom table prefix.
- Initialize the PostgreSQL schema with the exact same Core version and the same custom table prefix. Upgrade Core only
  as a separate, subsequently tested operation.
- Use a new target with no pre-existing SuperTokens application data. Never merge the source into a target that has
  accepted writes.
- Keep both databases and Core instances on private networks. Do not expose either database or Core publicly during the
  migration.
- Prove that a MySQL backup can be restored before the maintenance window. After writes stop, take the final source
  backup. Also define how the PostgreSQL target will be reset if an attempt fails.
- Schedule a write outage. Stop every Core and other process that can write to the source, and keep the target Core
  stopped during import and validation.
- Define an explicit rollback point and keep MySQL as the authoritative database until every acceptance check passes.

## Steps

<Steps>

<Step title="Build and test the import">

The import implementation must be built and tested for the exact released source and target schemas. It must:

- use explicit table and column lists and one binary-safe transfer contract that defines character encoding, escaping,
  line endings, `NULL`, empty strings, headers, and binary values;
- handle schema-specific conversions, including WebAuthn public-key bytes and third-party provider scope arrays, without
  parsing text in a way that may lose information;
- run in one database session and transaction, fail on the first error, and roll back the entire attempt rather than
  continuing or reporting partial success;
- use a dependency order proven against the matching released schema;
- preserve or restore trigger and constraint behavior in the same transaction, and validate all foreign-key, unique,
  check, and not-null constraints before commit; and
- pass a disposable migration fixture containing empty and populated tables, SQL `NULL` and empty strings, tabs,
  newlines, backslashes, Unicode, JSON, binary WebAuthn values, and provider scopes, and prove the exhaustive
  reconciliation below before it is approved for production.

If these properties have not been demonstrated by an automated fixture, stop and ask SuperTokens support or a
maintainer for assistance. Equal row counts alone are not evidence of a safe migration.

Run the approved implementation against the new PostgreSQL target only while every source writer and the target Core
remain stopped.

</Step>

<Step title="Reconcile the data">

Before starting the PostgreSQL Core:

1. Compare row counts for every source and target table. Any missing, extra, or skipped table is a failed migration, but
   matching counts alone are not sufficient.
2. Reconcile every source row to exactly one target row by its complete primary key, including every column of a
   composite key. Missing, duplicate, or unexpected keys are migration failures.
3. Compare every migrated value using a deterministic, per-table normalization contract reviewed for the exact
   MySQL and PostgreSQL schemas. Sort canonical rows by the complete primary key, encode field boundaries and types
   unambiguously, and distinguish SQL `NULL`, empty strings, empty arrays, and empty objects. Compare the canonical
   streams directly or compare hashes produced from those streams only after the support-assisted review approves the
   canonical representation and hash choice; this page does not prescribe a cross-database hash algorithm.
4. Include every column in that comparison, explicitly including password hashes, session records and payloads,
   signing keys, tenant and user-to-tenant mappings, timestamps, escaped and Unicode text, binary WebAuthn values, JSON,
   and third-party provider scopes. Normalize a value only where the released schemas require a representation change,
   and document and test each normalization.
5. Validate all target constraints and confirm that no staging tables, disabled triggers, or partially imported rows
   remain.
6. Retain the source backup and untouched source database for rollback.

</Step>

<Step title="Validate the PostgreSQL Core">

Start the PostgreSQL Core on the private network only after every reconciliation check passes. Then verify:

- Core starts without schema or constraint errors and its `/hello` endpoint responds;
- existing users can sign in;
- an existing session can refresh;
- each enabled recipe passes a smoke test, including account creation or sign-in and its critical follow-up operation;
  and
- logs contain no storage, decoding, or constraint errors.

</Step>

<Step title="Cut over traffic">

Cut application traffic over only after all checks pass. If any reconciliation or smoke test fails, stop the PostgreSQL
Core, return traffic to the unchanged MySQL deployment, preserve the failed target for investigation, and follow the
tested rollback procedure.

</Step>

</Steps>
